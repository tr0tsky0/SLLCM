# Skyborne Ley Line & Convergence Marker - project notes

Renamed from LeyLineMarker (v0.2.0). Folder/toc `SkyborneLeyLineConvergenceMarker`, SavedVariables `SkyborneMarkerDB`, slash `/sllcm`, data global `SLLCM_Data`. CurseForge project ID unchanged.

**Goal:** WoW: Forever addon that shows Skyborne leylines on the zone map. They show on the minimap but not the world map. Read Leyline (Alliance, spell 1259705) / Skysight (Horde, spell 1259686) last 15 min on one instead of 15/30 s.

**Keep it simple.** The public addon is a list of points + map icons; the list is updated by hand from reports. v0.2.0 adds a self-gatherer (15-min buff >= 600 s on 1259691 Energized Alliance / 1270893 Elemental Blessing Horde records your position), a 'self-found only' setting, and `/sllcm export`. Data.lua has `LeyLines` (Alliance) and `ElementalConvergences` (Horde, empty so far).

**Install:** Forever is `D:\World of Warcraft\_forever_` (interface 16001; was `_classic_beta_` until launch, 2026-11-04). Addon folders in this project are junctioned into `_forever_\Interface\AddOns\`.

## Addons
- `SkyborneLeyLineConvergenceMarker/` (public): `Data.lua` holds `SLLCM_Data.LeyLines[mapID] = { {x, y}, ... }`; `SkyborneLeyLineConvergenceMarker.lua` pins them via a WorldMapFrame data provider, `MagePortalAlliance` atlas. MapCanvas pins must NOT set OnLoad/OnEnter/OnLeave scripts in XML (canvas wires them and asserts). `SetPassThroughButtons` is protected in combat, so the pin skips `CheckMouseButtonPassthrough` during `InCombatLockdown()`.
- `LeyLineTest/` (personal, not released): records leylines from minimap blip hovers (cursor offset -> yards via `C_Minimap.GetViewRadius`, ~15-20 yd accuracy) and racial casts (any >=600 s buff starting at cast = on a leyline). Saves to `LeyLineTestDB[mapID] = { {x, y, confirmed}, ... }`, flags whether each is already in Data.lua. `/llt` lists ones not yet in Data.lua; `/llt here`, `/llt add mapID, x, y`, `/llt pos`.

## Verified in beta
- Leylines are not vignettes or area POIs; only visible as a minimap blip with GameTooltip line 1 = "Leyline" ("Ley Line" until Blizzard renamed it, seen 2026-10-18; the racial is now "Read Leyline" too) (owner UIParent; detect with `Minimap:IsMouseOver()`).
- Minimap-hover maths checked in Westfall (rotate off): both axes right sign, within blip-edge error.
- Racial buff detection recorded a confirmed point in Westfall.
- `/llt pois` and `/llt vignettes` (added 2026-10-06) check whether leylines/convergences have become visible to the API; any name or atlas with "ley"/"converg" is flagged `!!`. As of 2026-10-06: zone maps have no area POIs (the only ones seem to be capital-city markers on the continent/world map) and no vignettes, even standing on a convergence (Horde char). Worth re-checking after client patches.

  - Finding candidates: every `R`/`S`/own sighting stamps `db.seen[key][mapID]` (`{x, y, t}`, newest per spot) and `db.activeDays[key][mapID][day]`; both forget after 60 days. Days run from 10:00 UTC (`DAY_START`): with UTC midnight, one evening in the channel (16 Nov, 19:02-03:12 UTC, 168 spots in 38 zones) counted as two. Days saved before that are rebuilt from the stamps once (`db.dayStart`). `/sllcm export` lists **suspects**: Data/self-found/shared nodes whose zone has had 5+ active days (`SUSPECT_DAYS`) since they were last seen, plain age doesn't count, so quiet low-level zones say nothing. Plus "retired but seen" (retired points with a sighting on record). Stamps start empty, so nothing is suspect until about 5 active days after the release. `L` locations never stamp: they're claims, not sightings. Not done: the "only re-send shared locations a sighting confirmed" change to L answers.
  - Crowd vouches (`VQ` / `V`, built 16 Nov 2026, untested in game): `/sllcm share vouch` (dev copy) sends a `VQ`; every answer is, per zone, a bitmap over Data.lua's list of the nodes that client saw lately, plus the zone's active days and a list checksum (`docs/SHARING_PROTOCOL.md`). So one `share vouch` on a Horde alt brings back the Horde crowd's verdict. Merged into `db.vouch` (14 days); zones from another release's list are skipped. Export comment adds `crowd N days, M answers`. Only Data.lua nodes; shared ones get vouches once merged into Data.lua. Tests: `python tools/test_nodes.py`.
  - Why bad points stuck: L entries carry no proof, every client re-sent its `db.shared` in F answers, and `db.shared` never forgets; 1,352 of Data.lua's ~1,900 points came from shared.
- Announce found nodes on login: built 15 Nov 2026 (Comm.lua `Announce`, untested in game). Self-found only, no threshold: once the channel is heard, 30-90 s later, unless an L with entries went out under 20 h ago (`db.foundSentAt`) or this session answered an F. L's heard during the wait cover ours. Answers to `share found` now also carry shared locations, one L at a time with what others' L's had left out, so the dev's F pulls the whole crowd's "seen but not in Data.lua" pool. ## Dev and released copies (set up 2026-09-30)
- `AddOns\SkyborneLeyLineConvergenceMarker-Dev` is a junction to `SkyborneLeyLineConvergenceMarker/` here; it loads through `SkyborneLeyLineConvergenceMarker-Dev.toc` (same files, "(Dev)" title, no CurseForge project id so WowUp can't match it). **Leave that file out of release zips.** Build them with `python tools/package.py`: it zips only the release toc and the files it lists into `dist/` (gitignored), so dev-only files (the -Dev toc, `Watch.lua`) stay out.
- **Scanning is broken on the live client (found 2026-11-17, see `notes/wow-api.md`):** the soft-cursor probe returns no tooltip lines anywhere, and a hovered blip's tooltip comes back as one secret line. So Scan.lua (and the controller / hover fallback) finds nothing; only racial casts detect nodes now. Deliberate: a Forever update around 14 Nov 2026 made minimap data secret (Blizzard forum thread t/2415197, a gathering-node addon's author). Since then last-seen stamps come only from racial casts, which players make at nodes they already know, so a real node nobody walks to will look unseen: weigh export suspects with that in mind. Racial range measured the same day: buff at 24 yd, not at 30 yd.
- `Scan.lua` (both copies, released in 0.4.0 on 2026-10-14): reads node blips off the minimap without the mouse via
  the soft cursor (coarse 8-unit grid; touching hits grouped into one blip; fine 2-unit grid over each blip). Verified
  in game 2026-10-14 against a racial-confirmed Redridge node (30.28, 55.06): about 1 yd off from 182 yd away, with
  and without a rotating minimap, on a 226-unit square minimap where a blip's tooltip area was about 25 units across
  (156 fine points). Dev diagnostic: `/sllcm scan` (status, then one verbose scan; keep it out of public text). Hits are recorded as self-found (quietly if Data.lua has
  them) and shared through `SLLCM_ReportSighting`. Setting "Detect nodes on the minimap" (`db.minimapScan`, on by
  default). Approach from the Skyborne Compass author (Oct 2026); written from their description, not their code.
  With a controller (`InputUtil.IsGamepadUIEnabled()` or `SoftCursor` shown; NOT the `GamePadEnable` CVar, which was
  on for a keyboard player on 2026-10-14) it doesn't scan, since the game owns the
  minimap soft cursor; it watches the mouse or the global `SoftCursor` frame on the minimap instead and records a blip
  it rests on (hover accuracy, ~20 yd). LeyLineTest's own hover recording stands down while
  `SLLCM_MinimapDetection()` is true. `python tools/test_scan.py` simulates both, including a rotating minimap.
- `Watch.lua` (dev only, in the -Dev toc): watches incoming sightings for unsure Data.lua points (its `WATCH` table) and saves hits to `SkyborneMarkerDB.watchHits`; `/sllcm watch` lists them, `/sllcm watch clear` resets.
- `AddOns\SkyborneLeyLineConvergenceMarker` should be the real released copy (v0.2.1 zip extracted), ignored or managed by WowUp, not a junction.
- Only enable one of the two at a time: they share globals (`SLLCM_Data`, the pin template, `/sllcm`) and `SkyborneMarkerDB`.

## Sharing (v0.3.0, Comm.lua)
- Full protocol (shared with Mapzeroth's LeyShare.lua): `docs/SHARING_PROTOCOL.md`. Update it whenever Comm.lua's wire or Q/S behaviour changes.
- Hidden per-faction channel `SLLCMShareA`/`SLLCMShareH`, prefix `SLLCM`. Messages: `R` (sighting), `Q` (request for a phase), `S` (reply). Forever megarealms mean the channel reaches the whole faction on a ruleset.
- Phase = zoneUID from creature GUIDs (same as War Effort, which is all rights reserved: don't copy its code). Saved over /reload for 5 min.
- "Not there" reports from Skyborne Compass (`XM` / `XS`, 0.4.1): received, never sent. The newest report per node
  and phase wins: a newer XM moves a sighting out of `db.crowdReports` into `db.crowdGone` and the pin greys out.
  Dev `Watch.lua` logs sighting-to-gone times (`/sllcm watch life`), to pin down node lifetime. Tested by
  `python tools/test_comm.py`.
- Own sightings (racial, scan) are kept in `db.crowdReports` (`mine`) even with sharing off (0.4.1): nothing is sent,
  the pins still turn green, unsighted opacity (`db.unseenAlpha`, 0-100, 0 hides; replaced the `hideUnseen` checkbox) works from your own finds, and
  Mapzeroth reads them. With sharing off the map shows only `mine` sightings.
- Sightings (`db.crowdReports`) fade green to red over `TTL` (90 min, top of Comm.lua; a node was seen up 58+ min on 2026-10-12), then are dropped. Locations from others (`db.shared`) never expire; removed only once Data.lua has them. Not learned or shown while self-found only is on.
- **Forever refuses addon messages on custom channels** (since launch, 4 Nov 2026; still on build 70862). `SendAddonMessage(..., "CHANNEL", id)` returns 0 (Success), then `CHAT_MSG_CHANNEL_NOTICE` `NOT_ALLOWED_IN_CHANNEL`, no echo. (`AreOutgoingAddonChatMessagesRestricted()` is no guide: still true on 12 Nov while channel messages were delivered both ways; probably about addon chat text.) Delivery worked on 12 Nov (Alliance, `SLLCMShareA`: others' R/Q/S/XM heard, ~90 L answers to one F), with no hotfix note saying so; whether that's a fix or intermittent is unknown. Whispers work, GUILD was fixed. Same for QuestTogether, ForeverLFG, War Effort (r/wowaddons thread "WoW: Forever — addon CHANNEL returns Success, followed by NOT_ALLOWED_IN_CHANNEL"). Not ours to fix: we wait for Blizzard; no guild/party fallback (too limited; if it stays, sharing goes). So a `>>` in debug proves nothing: only a message heard on the channel (our echo or anyone's) does.
  - Comm.lua: `NOT_ALLOWED_IN_CHANNEL`, no echo within 15 s, or `InvalidChannel` that a rejoin doesn't fix → `Refused`: nothing sent for 10 min, then the next message is the probe; "working again" only when something is heard. No "relog" advice (it never helped).
  - The channel can also end up greyed out (`GetChannelList`'s third value `true`; sends `InvalidChannel`, `/leave` `NOT_ALLOWED_IN_CHANNEL`, `/chatwho` `INVALID_NAME`). 11 Nov (Normal ruleset, Alliance): `SLLCMShareA` greyed at login while `WarEffortPvEA` and a freshly `/join`ed `SLLCMProbeA7` were active on the same cluster, so it's per channel, not all custom channels; the same evening RP Horde (`SLLCMShareH`) worked (~80 L answers). Each ruleset is its own megarealm, so the four channels (RP/Normal × A/H) are separate server-side and can differ. Leave + rejoin never cleared it (the leave itself is refused); a manual `/chatwho SLLCMShareA` did: `INVALID_NAME`, the client dropped the channel, a fresh join was heard at once (one sample; the server may have lifted it by itself). So `Freshen` now sends `ListChannelByName` (`/chatwho`, its answer kept out of chat), joins fresh if the client drops the channel within 4 s, and only otherwise leaves and joins again; the first 2 a session may be 15 s apart (a login revive must leave one for the first refused send), then every 2 min, 6 a session. `/sllcm share found` says "asked" only when the F actually goes out, "not sent" if it's dropped. `Freshen` runs when found greyed out, and `YOU_LEFT` / `INVALID_NAME` / `SUSPENDED` / `NOT_MEMBER` on our channel recheck it. Chat channel calls go through `securecall`; with sharing off the channel isn't touched at login. Check by hand: `/run local t={GetChannelList()} for i=1,#t,3 do print(t[i],t[i+1],t[i+2]) end`.
- Off until the player answers the first-run popup (`db.crowdAsked`). Debug: `/sllcm share` (status), `share debug`, `share reset`. Dev copy only (Watch.lua's `ns.DevShareCommand`, since 16 Nov 2026; Comm.lua keeps the hooks `ns.Ask`, `ns.TestSighting`, `ns.TestClear`): `share found`, `share vouch`, `share test send|receive|new|clear` (local only, never sent). Also dev copy: `/sllcm share debug window` sends debug lines to SLLCM's own window (`DebugWindow.lua`, -Dev toc only; place, size, on/off in `db.debugWindow`; close hides it but lines keep coming; the command again shows it, then turns it off; Copy shows the lines selected, colors off, for Ctrl+C: addons can't write the clipboard). `share found`'s own lines ("asked", "found locations from ...") go there too when it's on, debug or not. The 60 s ticker's join while we were hearing the channel happened again at 23:48 on 11 Nov with the channel-list check in: the client really didn't list it; the `joining` line now logs what GetChannelName gave and the whole channel list. New files in a toc load only after a full game restart, not /reload. A chat window of ours wasn't enough: Daylight UI's chat box reads every window's lines into its own tabs by kind, so addon lines land with "system" wherever the window.
